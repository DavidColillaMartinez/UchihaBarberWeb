# Prompt para OpenCode: primera prueba de continuidad

He aplicado sobre este repositorio la entrega de documentación/herramientas de las fases 1.5–2. Te autorizo a revisar y corregir esta integración dentro de ese alcance, retirar del seguimiento los dos archivos personales indicados conservándolos localmente, registrar el ensayo, hacer un commit y publicarlo en el remoto actual del proyecto. No implementes secciones ni modifiques el diseño de la web. No reinicialices Git, OpenSpec ni las skills.

1. Lee AGENTS.md, PRODUCT.md, memoria/README.md, protocolo.md, integraciones.md, estado.json, aplicacion.md y el último relevo. Explica brevemente qué gobierna cada fuente y cuál es el trabajo permitido. Inspecciona el Git real (estado, HEAD, rama, remoto y diffs); no des por sincronizada esta copia. Detecta cambios ajenos y no los incluyas ni sobrescribas.
2. Ejecuta `npm run memoria:check` y `npm run memoria:changes`. Al principio puede fallar por los dos archivos personales todavía seguidos o por diferencias locales. Lee y explica las diferencias antes de escanear. No publiques rutas/URLs con credenciales ni consentimientos.
3. Comprueba con `git ls-files` y `git diff --cached` las rutas `.impeccable/config.local.json` y `.codex/hooks.json`. Retira solo las que sigan versionadas con `git rm --cached -- <rutas>` sin `-f`; comprueba que los archivos locales siguen presentes. Si hay cambios ajenos preparados que impiden hacerlo, conserva esos cambios y explica el conflicto. No borres archivos locales ni reescribas historia.
4. Comprueba Node/npm disponibles, `npm run memoria:test` y el formato solo de archivos nuevos/modificados de la entrega con el Prettier local. No formatees skills/comandos generados que no hemos cambiado. No instales nuevas dependencias; el lockfile no ha cambiado. Si necesitas reponer las existentes, respeta npm y el lockfile. Como se modifica tooling y documentación, un build no es una prueba de la integración SDD; ejecútalo solo si detectas impacto real en la web.
5. Ejecuta `openspec context --json` desde esta raíz. Confirma la raíz devuelta y que la configuración transmite referencias a AGENTS, PRODUCT y memoria. Inspecciona la ayuda/versión disponible si el comando o campos no son compatibles. Comprueba que los comandos/skills instalados siguen presentes. No inventes cambios OpenSpec para representar este mantenimiento y no declares probado Impeccable si no has podido ejecutarlo. Si falta la CLI o hay un bloqueo, registra exactamente qué comprobación falta; no marques la fase aprobada.
6. Crea un relevo nuevo, por ejemplo `memoria/sesiones/SES-002-ensayo-local.md`, con agente, objetivo, base Git, diferencias observadas, revisión de documentos, comandos y resultados reales, configuración retirada del índice, limitaciones y siguiente paso. Actualiza `ultimoRelevo` y evidencias en estado.json. UB-001 puede aprobarse si cumple todos sus criterios. UB-002 queda en revisión hasta confirmar commit/push real; no anticipes ese éxito dentro del commit que aún no existe. Ninguna sección queda aprobada por esta prueba.
7. Corrige únicamente fallos de esta integración, formatea lo tocado y ejecuta `npm run memoria:scan`, `npm run memoria:check` y `npm run memoria:test`. Revisa el diff de índices y todo el diff que vas a publicar. Si un control relevante falla sin resolver, informa el bloqueo y no publiques una integración marcada falsamente como correcta.
8. Inspecciona remoto/rama y, con acceso disponible, actualiza referencias mediante fetch para comprobar que el push no sobrescribirá trabajo remoto. No hagas force-push ni pull a ciegas. Añade al índice rutas explícitas de esta entrega y tu relevo; no uses `git add .` para incorporar cambios ajenos. Puedes usar como base AGENTS.md, PRODUCT.md, README.md, .gitignore, .prettierignore, package.json, openspec/config.yaml, memoria/ y scripts/memoria/, tras revisar su contenido. Las dos retiradas ya estarán preparadas. Examina `git diff --cached --stat` y `git diff --cached` antes del commit.
9. Si los controles están correctos, haz un commit con mensaje breve en español, por ejemplo `Integra memoria compartida y reglas de IA`. Ejecuta `npm run memoria:check` después: debe pasar aunque HEAD haya avanzado. Publica en el remoto/rama reales sin forzar. Si el push se rechaza o falla, conserva el commit y comunica el motivo; no declares sincronización ni rehagas historia por tu cuenta.
10. Devuelve SHA completo obtenido de Git, resumen de cambios, pruebas y resultado real del push (compara la referencia remota con HEAD si tienes acceso). No hagas un segundo commit solo para insertar su propio SHA. En la siguiente sesión se incorporará ese SHA y el resultado confirmado a un nuevo relevo y se cerrará UB-002 si satisface sus criterios. Termina aquí: empezar la web requerirá mi instrucción de la fase siguiente.

Esta es una prueba del protocolo: demuestra que puedes recuperar el contexto, detectar cambios, distinguir escaneado/revisión/aprobación y dejar un relevo útil para cualquier otra IA. No repitas preguntas de autorización ya resueltas en este prompt.
